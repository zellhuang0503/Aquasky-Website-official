# AquaSkyPlus 官網重建與 Cloudflare 搬遷初步評估

日期：2026-09-24。黃老闆已選定方向：**保留網址與主要內容、改善版型；不要 CMS，以 AI agent 協助維護。** 備份取得狀況：目前不確定，依使用者回覆先以公開網站估算。

本文是可供決策的初步研究與分階段計畫，尚非核准開發規格。本次沒有修改網站程式、部署、DNS 或正式站內容。框架查證見 [官方資料研究](2026-09-24-framework-options.md)。

## 1. 推薦架構

採用 **Astro + TypeScript + 結構化內容檔 + Cloudflare Workers Static Assets**。

- 公開產品、文章、FAQ、公司頁在建置時產生 HTML。
- 產品共同規格存 JSON／YAML，翻譯文字與文章存 Markdown；用 Astro Content Collections 檢查欄位。
- 版型改成共用 Astro 元件，僅選型計算器等必要區域使用互動 JavaScript。
- 詢問表單由 Worker API 驗證、限流，再透過選定的寄信服務傳送；使用 Turnstile 時必須由伺服器呼叫 Siteverify。
- 大型 PDF／素材如超出 Static Assets 限制，可使用 R2 並設計原網址對應。第一版不預設需要 R2 或內容資料庫。
- 純靜態 Astro 不需要 Cloudflare adapter；只有需要 Astro 即時伺服器渲染時才加入。

依據：[Cloudflare Astro 指南](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/)、[Astro Content Collections](https://docs.astro.build/en/guides/content-collections/)、[Turnstile 伺服器驗證](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)。推薦是針對本案內容型官網與無 CMS 需求的判斷，不是框架的通用排名。

## 3. 到底會改多少

這是「底層重建、內容搬遷、版型改善」，不能用沒有依據的單一百分比估算。

| 層面 | 預定處理 | 變動程度 |
| --- | --- | --- |
| 網域與現行公開網址 | 逐筆保留；必要差異做明確對應 | 以最小變動為目標 |
| 品牌、主要文字、產品事實 | 保留已確認內容，轉成結構化檔案 | 內容少改、儲存方式全面轉換 |
| 圖片、PDF、影片 | 搬移或保留外部來源，保留下載 URL／連結關係 | 視素材盤點結果 |

| PHP 網頁產生與 CMS | 前者由 Astro 建置取代，後者取消 | 全面替換 |
| 官網內容資料庫 | 匯出後改內容檔；是否另需交易資料儲存依功能確認 | 公開內容預期不再依賴資料庫 |
| 聯絡表單 | 新寫 API、驗證與寄信流程 | 重做並驗證送達 |
| 選型工具 | 先取得公式／原始碼與基準案例，再保留或重寫 | 工作量未知，獨立估計 |

791 筆網址不等於手刻 791 個版面。初估可先規劃約 **10–14 種共用頁型**；實際數量需清點產品特殊系列、下載與選型工具後確定。頁型數只是設計工作假設，不是已確認的完整清單。

## 4. 內容與 AI 維護設計

建議另建私有官網倉庫，例如 `aquasky-website`（名稱待建立時定案），把既有 AEO／監測倉庫保留作歷史與維運來源，避免將提案、報價或內部報告包含在網站建置輸出。

內容結構原則：

- 每個產品有固定 ID；規格共用，語系文案分開，避免六份數字漂移。
- 每篇文章保留原 URL、語言、標題、日期、圖片、SEO 與來源對應。
- URL 是獨立欄位，不隨標題改名自動更動；大小寫及尾斜線策略明確。
- 阿拉伯文需檢查 RTL 版型；缺譯內容明確標示，不由 AI 猜測補齊。
- JSON-LD 與頁面使用同一份資料，規格與認證不能只出现在 schema 而正文沒有。
- 產品性能、認證、保固與計算公式必須有客戶依據；型別檢查不能代替事實審核。
- `AGENTS.md` 定義可改範圍、來源要求、必要檢查、正式部署與回復方式。

日常流程：**黃老闆提出需求 → AI 修改分支 → 自動檢查 → 獨立預覽與差異摘要 → 第一關梵亞內部審核 → 第二關客戶審核 → 發布同一核准版本 → 線上驗證**。

Dashboard 的建議不直接觸發正式發布。客戶透過受限的臨時預覽頁查看實際文字、圖片、排版與互動，核准紀錄綁定具體版本；退回修訂後重新走兩關，缺核准或版本不符不得發布。狀態為草稿、內部待審、客戶待審、已核准待發布、已發布。詳細規則見[整體規劃第 8.3 節](../2026-09-24-AQUASKY官網改版與AI維護整體規劃.md)。

例如「更新某型號中文介紹與 PDF」：AI 只改指定內容與附件引用，保留產品 URL，提供預覽；確認後重新建置發布。內容更新需要一次建置，不是 CMS 按儲存即時寫入資料庫。

無 CMS 不等於無維護：仍需維護相依套件、備份、寄信服務、部署權限與內容來源。第一階段不必另建常駐自主發布 agent，先把 AI 修改流程做可靠。

## 5. 分階段計畫與估時

以下為規劃估算：一位熟悉此架構的工程執行者搭配 AI、素材可取得、客戶適時提供回覆；不是固定報價或交期承諾。

| 階段 | 交付／完成條件 | 初估工作天 |
| --- | --- | ---: |
| 1. 完整盤點 | URL／頁型／語系／素材／表單與工具清冊，取得備份；確認保留範圍 | 2–4 |
| 2. 小範圍試作 | 首頁、系列、產品、文章代表頁；中英文及阿拉伯文版型；一條表單流程、選型工具技術檢查；確認 Cloudflare 預覽可行 | 3–5 |
| 3. 共用版型與內容搬遷 | 約 10–14 類頁型、六語系實際資料、附件與舊 URL 對應，產出缺漏報告 | 8–14 |
| 4. 功能／SEO／AEO 整合 | 表單送達、已確認範圍內的選型工具、301、canonical、hreflang、schema、sitemap、追蹤 | 4–7 |
| 5. 驗收與切換 | 分類驗收、修正、備份、Cloudflare 切換與回復演練 | 3–5 |
| 合計 | 有完整可用資料時的暫估 | **20–35** |

約 4–7 個工作週，不含等待備份、商業事實確認與追加功能；上線後另安排 2–4 週觀察，不等於每天投入一整天。

黃老闆目前不確定能否取得備份，要求先以公開網站估算。因此主情境為：在上述基準上暫加 **5–10 工作天**做內容抽取與核對，合計 **25–45 工作天，約 5–9 個工作週**。大量缺圖、錯誤翻譯、隱藏功能、無公式的選型工具須另估，不能保證落在此區間。內容搬遷可批次處理，但只有取得實際資料後才能縮小估時。

公開網頁可取得的是輸出後的 HTML 與公開素材，不能由此還原 PHP 原始碼、資料庫、未公開內容或伺服器寄信設定。選型工具若只能觀察結果，仍需原廠公式或工程人員確認的測試案例才能宣稱重建等價。

優先順序：先完成「盤點＋代表頁試作」再承諾全站範圍。六語系搬遷可以內部按批驗證，正式切換前仍以已確認要保留的全站完整度為門檻。

## 6. SEO、既有 Cloudflare 與切換

過渡採舊站正常營運、新站獨立建置，雙關審核及驗收後切換。5–9 工作週是工程估算，客戶等待及修改往返另列排程；第一週盤點完成後再縮小範圍與確認日期。切換前以舊站正式內容為基準，記錄施工期間更新並同步到新站；建議切換前 1–2 工作天凍結一般編輯，網站保持服務，緊急修改同步兩邊並重新審核受影響版本。切換後改用新站維護流程。

上線後先安排約 2 週密集觀察，必要時延長至 2–4 週；舊站受限保留約 2–4 週至驗收、觀察與回復準備完成，確認郵件等相依後才退租。詳細階段窗口與同步方式見[整體規劃第 13 節](../2026-09-24-AQUASKY官網改版與AI維護整體規劃.md)。

- URL 原則上原樣供應 200；只有確定改址的頁面做一對一永久導向，避免全部回首頁。
- 舊 `.php?sid=...&lang=...` 等參數需建立對照；Workers Static Assets `_redirects` 不支援 query 條件匹配，應用 Worker 或適用规则處理。
- 新站自己輸出 canonical 與結構化資料後，先在預覽核對，再逐項解除舊 AEO HTML 注入，避免重複與互相覆寫。
- 原始與補充 sitemap 要整合；舊 sitemap 入口明確保留或轉接，避免監測與 Search Console 的既有引用斷掉。
- 先備份實際 DNS、Routes、Redirects、WAF 與 Worker 設定；現有路由會不會攔到新站，須在上線方案明列。
- 舊站以受限方式保留到切換驗收與觀察完成。原 AEO 的 `AEO_ENABLED=false` 只是停止改寫，**不等於新站搬遷回滾**；回滾要能復原主站路由／來源站配置及相符的 AEO 規則。
- 確認原主機是否另含 email 或其他服務，完成相依檢查才退租；網站切換不可誤改郵件 DNS。
- 預覽先設存取限制並避免索引。保留網址也不能保證排名完全不波動，需比較基準與上線後數據。

依據：[Google 不改網址的主機搬遷](https://developers.google.com/search/docs/crawling-indexing/site-move-no-url-changes)、[Google 改網址搬遷](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)、[Cloudflare redirects](https://developers.cloudflare.com/workers/static-assets/redirects/)。

## 7. 驗收與成本邊界

正式上線前至少完成：

1. 已核准的 URL 清冊全部有去向，抽樣加自動檢查內容、圖片及附件；確認沒有不預期的 404 或多跳導向。
2. 六語系導覽、hreflang、canonical、手機排版、阿拉伯文 RTL 正確。
3. 表單成功／失敗／重複提交有清楚狀態，指定收件匣實際收到測試信；HTTP 200 不等於送達。
4. 選型工具以站方提供的已知输入／输出案例回歸；無法確認公式時不宣稱功能等價。
5. schema 與可見內容相符，sitemap 是有效可索引網址；預覽限制不誤帶到正式站。
6. 用一筆真實內容修改走完 AI → 分支 → 檢查 → 獨立預覽 → 梵亞內部審核 → 客戶審核 → 發布同一核准版本；驗證退回重審、缺核准及版本不符不能發布。
7. 回復上一版本與恢復舊站路由有實際可執行步驟；保留切換前備份。

成本分為一次性重建／搬遷、Cloudflare 動態請求與可選儲存、寄信與監測，以及後續 AI／人工維護。静態流量目前免費不表示整套系統零成本；未取得素材容量、動態請求數、寄信量與服務方案前，不報固定月費。參考 [Static Assets 計費與限制](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)。
