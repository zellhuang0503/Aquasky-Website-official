## 架構結論

對外官網建議採 **Astro + TypeScript + 結構化內容檔 + Cloudflare Workers Static Assets**，表單與選型工具按需求另設動態功能。AI agent 協助官網內容與程式修改，經預覽與人工確認後發布。私人 Dashboard 維持獨立，架構與改造不屬於這次官網專案。

監測紀錄持續增加，不代表公開官網每一次瀏覽都需要即時從資料庫產生頁面。會變動的產品文案可以在確認後重新建置；監測輪次、原始答案與事件則存於動態資料層。無 CMS 不等於完全不使用資料庫。

Astro 是此維護模式下的首選，不是 AEO／GEO 成效的保證。PHP 同樣可以提供完整 HTML、正確 schema 與良好內容；目前讀到的線上結果與本地文件沒有證明「PHP 是 AI 誤認或不提品牌的原因」。重建的價值在於取消 CMS、取得内容與部署的維護自主性、统一可驗證資料與減少依賴原主機；AEO／GEO 成果仍需另驗。

## AEO／GEO 與 SEO 的共同設計

1. **完整可讀的 HTML**：產品規格、用途、FAQ 與證據摘要在初始頁面可見；互動只補充體驗，不把主要答案藏在登入或需點擊才取資料的區域。
2. **同一份已核准事實**：產品數字、認證、保固及 MOQ 由結構化欄位供頁面與 schema 使用；語系文案分開，事實避免多處手填。
3. **答案有範圍、有依據**：先直接回答問題，再列適用／不適用條件、規格表與證明文件；不為了引用機會虛構優勢或認證。
4. **保留網址與內容關係**：固定 URL、canonical、hreflang、產品與系列關係、相關文章與下載內部連結。主站更新不強迫更換所有路徑。
5. **搜尋與 AI 存取分開檢查**：索引資格、robots、WAF、搜尋爬蟲與訓練用途政策各自確認；不能用「全面放行所有 bot」取代查證。
6. **新站原生輸出 AEO 所需資訊**：現有補強 Worker 的 canonical／schema／sitemap 功能經對照後搬入新站，再逐項停用重複注入；導向、防護與監測按需延續。
7. **保留既有 SEO 基準**：切換前記錄重要 URL 的搜尋表現、索引與詢問轉換；切換後按相同口徑追蹤。現在尚未讀取 Search Console／網站分析／業務詢問紀錄，不能承諾排名維持或詢問量提升幅度。

官方原則與限制見另附 `2026-09-24-aeo-geo-requirements.md`。Google 的 AI 搜尋建議持續要求可爬取、可索引、有用且可靠的內容；特定框架、特製 AI 檔案或 schema 並非自動被引用的捷徑。[Google AI features](https://developers.google.com/search/docs/appearance/ai-features)

## 從監測到修改的可追蹤流程

**保存一輪證據 → 檢查是否完整且可比較 → 判斷問題 → 找到相關 URL 與已核准來源 → AI 提出修改 → 自動檢查與預覽 → 人工確認發布 → 記錄版本 → 用同條件觀察。**

每項修改建議連結以下欄位：問題／事件 ID、輪次、原始答案與引用、相關 URL、已確認事實來源、修改目的、Git commit、上線時間、驗收結果，以及後續同題結果。這是建議新增的連結關係，不能宣稱目前 dashboard 已完整具備。

兩種狀態分開：

- 工作狀態：提案、核准、已發布、技術驗收通過。
- 效果狀態：待觀察、未見改善、有變化但未確認原因、在可比較條件下持續改善。

監測資料可以自動累積；公開官網應只接收已核准且有來源的內容。不能將 AI 誤答自動寫回產品事實，也不應因單次分數波動就自動改站。

## 如何衡量是否值得改

| 層次 | 要回答的問題 | 不能當成什麼 |
| --- | --- | --- |
| 存取 | 合法爬蟲是否取得正常頁面與正文？ | HTTP 200 不等於已引用 |
| AI 曝光／回答品質 | 是否認對品牌、說對條件、引用正確頁面？ | 品牌字串出現不等於推薦，API 測試不等於真實使用者曝光 |
| 真人來源流量 | 是否有可辨識為 AI 或自然搜尋來源的真人進站？ | 引用次數不等於訪客，來源標記也可能遺失 |
| 商業結果 | 是否帶來有效詢問及後續商機？ | 流量不等於詢問，表單點擊不等於送達 |

本地程式已把完整月測與重點複查分開；比較要求題文、模型、搜尋設定及回答完整性一致。9/24 文件記錄 Claude 型號變更，應另立新基準；不能把模型更換造成的差異歸功於網站修改。也要明確區分 API 測試與消費者實際使用的聊天介面。

資料累積還需補上保存與備份政策。本地文件記錄證據儲存有應用層上限與停止寫入保護，不能假設可以無限累積；何時歸檔、備份驗證、如何仍能查回原證據，應列為監測系統的獨立維運工作。

## 建議採行順序

1. **補齊基準缺口**：本次已確認監測中心的歷史／即時與輪次區分；下一階段補 Search Console、詢問與重要 URL 清冊，並對高優先事件保留未確認狀態。
2. **先做有價值的內容試點**：挑品牌身分、關鍵產品、保固／合作條件與選型內容。可以先在舊 PHP 站改善，無須等整站完成才開始；若更新受原廠限制，轉作 Astro 試作的代表頁。
3. **試作 Astro 與 AI 維護流程**：證明可保留網址、輸出完整 HTML、多語與 schema 一致，並走完一筆 AI 內容修改、預覽、核准與發布流程。
4. **再按頁型搬遷全站**：依前份盤點計畫搬內容、圖片與附件，處理表單與選型工具，整合舊 AEO Worker；不在全站切換同時大量刪文改網址。
5. **持續用監測決定下一批修改**：每次處理少量具體問題，保留變更與回測對照，不以單一總分代替實際結果。

目前不建議為了 AEO／GEO 改成全站即時 SSR 或另做完整 Next.js 應用；若日後確認有會員、即時報價、庫存或客戶入口，再獨立評估動態模組。框架選擇由功能與維護需求決定，內容優先順序由監測證據決定。
