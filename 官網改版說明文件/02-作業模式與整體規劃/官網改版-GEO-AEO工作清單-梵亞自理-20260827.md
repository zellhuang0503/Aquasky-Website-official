## 第二部分：⚠️ Worker 相關（工程師完工後，梵亞必須跟著改）

> 這一段全部依賴工程端完工後的實際 DOM 與 CMS 輸出。**網站改版上線 = Worker 一定要動**，否則輕則補強失效、重則結構化資料重複。

| # | 工作 | 原因 |
|---|------|------|
| W1 | **config.js 選擇器全面重對** | Worker 的內容收集全靠 DOM 選擇器；改版後 DOM 全變，舊選擇器會整組落空（落空 = 靜默不輸出，不會報錯） |
| W2 | **頁型判定重驗** | Worker 以頁面既有 JSON-LD 的 @type 判定頁型；CMS 自動生成 schema 後，各頁輸出內容改變，判定邏輯要重新實測 |
| W3 | **FAQPage 二擇一** | CMS 若輸出 FAQPage（工程文件 B8 開）→ Worker 不得再補，靠「既有已有則不重述」機制驗證；CMS 不輸出 → Worker 補，需為新 FAQ 版型寫收集選擇器（注意：產品頁的 FAQ 版型 ≠ /en/FAQ 的 sibling 交替結構） |
| W4 | **additionalProperty 分工** | 同 W3 邏輯：CMS 已把規格表轉 PropertyValue → Worker 略過；否則 Worker 需對新表格結構補選擇器 |
| W5 | **舊錯值必須先死透** | 同一 @id 的節點會被消費端**合併**：若後台舊 schema（butyl、NSF…）沒清乾淨就上新的，錯值與正確值會並存，比只有錯值更糟 |
| W6 | **網址異動處理** | 若工程端動到網址：301 之外，Worker 的 data/product-urls.json 與 /sitemap-aeo.xml 清單要同步更新，canonical 邏輯重驗 |
| W7 | **快取清除** | 上線時清 Cloudflare 快取（Worker 有寫 caches.default，舊頁面會殘留） |

### 上線後驗證（對應 AEO 案驗收條件）
